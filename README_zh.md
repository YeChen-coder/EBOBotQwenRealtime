## v3 能做什么

EBO 机器人的家庭语音助手，**不用唤醒词**，自然接话：

- **待机时在本机听写**：本地 Whisper（faster-whisper，CPU）分段转写。说"猫猫""小朋友"马上回应；其他话交给小模型（`qwen-plus`）判断是不是在跟它说，电视对白和家人之间的话都不理。
- **实时对话**：通义千问 `qwen3.8-omni-flash-realtime`，自带联网搜索。关掉了服务端 VAD，改成在本地判断一句话有没有说完，机器人自己的声音不会打断自己。
- **视觉跟随（可选）**：Frigate（YOLOv9-s，ONNX 跑在 NVIDIA 显卡上）从机器人画面里认人，看到人就转过去、靠近。连续 5 分钟没看到人，就原地找一圈，然后回充；跟它说"回去充电"，它会回充电座，并在一段时间内不追人。
- **看板**：http://127.0.0.1:8099/ ，有状态、实时画面（WebRTC）、对话和日志。

本项目是**自包含**的：机器人适配（EBO Engine）、人体检测（Frigate）、MQTT 和助手都在这里，不依赖 `ebo-ai-home`。

## 启动 / 停止

- 桌面上的 **启动EBO助手** / **停止EBO助手**（即 `scripts/start.ps1`、`scripts/stop.ps1`）
- 或命令行：`docker compose up -d` / `docker compose stop`

启动脚本会：必要时启动 Docker Desktop → 停掉会抢机器人的旧 `ebo-ai-home` 容器 → 启动全部组件 → 等就绪 → 打开看板。

- 看板（状态、实时画面、对话、日志）：http://127.0.0.1:8099/
- 机器人控制面板：http://127.0.0.1:8101/ （没有登录保护，只开放给本机）

## 从零部署

1. 装好 Docker Desktop。
2. 把 `.env.example` 复制成 `.env`，填上通义千问（DashScope）API Key 和 Engine Token。
3. 用你自己的 Enabot 账号和 App 加密 key 配置 Engine（本项目不附带这些 key，见 `engine/README.md`）。机器人配对信息在 `data/engine/`。
4. 按 [`frigate/models/README.md`](frigate/models/README.md) 里的命令导出 Frigate 模型 `frigate/models/yolov9-s-320.onnx`（权重是 GPL-3.0，没有放进仓库）。
5. `docker compose up -d`，或者双击启动脚本。

换电脑时，直接复制整个项目文件夹（含 `.env`、`data/engine/` 和模型文件），装好 Docker Desktop 再双击启动脚本就行。第一次启动会构建镜像、下载 Whisper 模型。要长期运行的话：Docker Desktop 设为开机启动，电脑不要睡眠。

## 配置与数据（都不要提交/外传）

- `.env`：通义千问 Key、Engine Token 和各项开关，参考 `.env.example`
- `data/engine/`：机器人账号与配对信息（`options.json` 等）
- `data/`：对话记录、回复录音（保留 7 天）、Whisper 模型缓存、Frigate 数据库

Why it kept repeating "我在听":

False wake: at 02:53 the TV was on, and Whisper produced a classic hallucination, "做一件事做一件事做一件事" (one phrase repeated three times). The AI judge took it as someone talking to the robot and woke it.
My timeout rule did the rest: after each turn the program waits for Qwen’s transcript. Under the old rule, if it wasn’t back within 6 seconds it replied anyway. Qwen’s transcription of TV noise is often slow (over 6 seconds) and comes back empty, so the model received empty turns again and again and could only answer "我在听".
It couldn’t stop:
Late transcripts were applied to the next turn as that turn’s text.
Each of those replies counted as activity, so the conversation never timed out. It went on for nearly half an hour.

Fixes:

No more blind reply on timeout: if Qwen’s transcript isn’t back within 3 seconds, this turn’s audio is transcribed with local Whisper instead (about 0.5 seconds). Empty means silence; real speech is still answered.
Transcripts are matched by turn ID: late ones are discarded, never applied to another turn.
Repeated-phrase hallucinations are filtered: text like "做一件事做一件事做一件事" no longer wakes it. Ordinary repetition like "你好你好" is unaffected.

## 一、语音

**A. 待机时（还没开始聊天）**
1. **听到声音，判断一句话说完了**（停顿约 0.9 秒）：WebRTC VAD，本地的声音检测算法，不是 AI 模型。
2. **转成文字**：本地 **Whisper small**（`Systran/faster-whisper-small`，CPU）。转之前先用 **Silero VAD**（faster-whisper 自带）滤掉不是人声的部分；转完用 **OpenCC** 把繁体转成简体。
3. **过滤没用的**（空的、“嗯嗯”、同一个词重复好几遍、零碎英文）：本地规则。
4. **安静模式中？**（18 分钟内有人说过“闭嘴”“不要说话”“你好烦”）：只认唤醒词，其他话不理，不调用任何云端模型。
5. **是不是“闭嘴”类的话？** 先本地查关键词，有的话再请云端 **`qwen-plus`** 确认。确认是 → 进入安静模式。
6. **是不是“回去充电”类的话？** 本地按读音查关键词（“空店”“通店”也算），有的话请 **`qwen-plus`** 确认。确认是 → 回充电座，**18 分钟不追人**。
7. **有没有唤醒词“猫猫 / 小朋友”？** 用 **pypinyin** 转拼音后按读音比对（“毛毛”“小盆友”也算），本地完成。有 → 马上醒。
8. **没有唤醒词** → 请 **`qwen-plus`** 判断“是不是在跟机器人说话”，同时参考最近一分钟听到的话，用来挡掉电视。是 → 醒。

**B. 对话中**

一句话的完整路线（多伦多是跑程序的电脑）：

```
国内家里：家人说话
  │  ① 机器人麦克风 → 声网 → 多伦多（Engine 收到）
  ▼
多伦多：程序
  │  ② 本地只判断“有没有人在说话、说完没有”（WebRTC VAD）
  │     边说边把声音压缩成 Opus，推给 ↓
  ▼
北京阿里云：qwen3-asr-flash-realtime 语音识别 → 文字传回多伦多
  ▼
多伦多：程序的判断逻辑
  │  ③ 没内容 / 纯噪声 → 不回
  │     “闭嘴”“回去充电”这类话，或者拿不准是不是在跟它说话 → 再问一次北京的 qwen-plus
  │     （机器人说完 20 秒内接的话，直接当作在回它，不用问）
  ▼
北京阿里云：qwen3.8-omni-flash-realtime 对话模型
  │  ④ 程序把“文字”发过去，它边想边把回答的声音流式传回多伦多
  ▼
多伦多 → Engine → 声网 → 国内家里的机器人喇叭
     ⑤ 收到一点声音就转发一点，不等整句说完
```

1. **判断一句话说完了**：WebRTC VAD（本地）。
2. **边说边把声音发给语音识别**：云端 **`qwen3-asr-flash-realtime`**，声音先压缩成 Opus 再发。
3. **拿到这句话的文字**：说完以后识别结果传回来；3 秒没回来，就用本地 **Whisper small** 再听一遍。
4. **没内容** → 不回答。
5. **“闭嘴”类**（**`qwen-plus`** 确认）→ 不回答，结束对话，进入安静模式。模型自己答应“那我就安静待着”“不打扰你了”时（本地查关键词，**`qwen-plus`** 确认）也一样：这句说完就结束对话，进入安静模式，不再挂着等超时。
6. **不是在跟它说话**（**`qwen-plus`** 判断，比如电视声）→ 不回答。
7. **“回去充电”类**（**`qwen-plus`** 确认）→ 回充电座，18 分钟不追人，同时照常回答。如果它自己说了“我这就回去”，本地规则也会让它真的回去。
8. **正常回答**：把这句话的文字发给 **`qwen3.8-omni-flash-realtime`**，它直接用声音回答，声音是**龙安灵心（`longanlingxin`）**，需要时会联网搜索。
9. **4 分半钟没有真正的交流** → 结束对话，回到待机。

另外，机器人麦克风的声音在进入以上流程之前，先经过 **Agora（声网）SDK 降噪**，这一步在 Engine 里完成。

## 二、图像（视觉跟随）

**A. 平时看人**
1. **取画面**：Engine 把机器人摄像头的画面转成视频流，**640×360，每秒 5 帧**。
2. **识别人**：**Frigate** 在画面有变化的区域运行 **YOLOv9-s（输入 320×320，ONNX，NVIDIA 显卡）**。
3. **算作“人”的门槛**：单帧分数 ≥ 0.5 开始跟踪；连续几帧的分数中位数 ≥ **0.6**；框的面积 ≥ **2500 像素**（太小的，比如窗外的剪影，不算）。满足后才通知我们的程序。
4. **我们的程序再筛一遍**：丢掉太小的框，丢掉包住真人的“幽灵框”；继续跟当前的人，没有当前的人就选画面里最大的那个。

**B. 怎么跟（本地规则，不用模型）**
1. **在充电座上** → 先笔直开出去（速度 70，2.5 秒），不在座上原地转。
2. **人不在画面中间**（偏差超过 6 度）→ **按角度转向**，一次转过去（最多 60 度）。
3. **对准了、人还很远**（框高度不到画面一半）→ 往前开：很远开 2 秒，稍远开 1.2 秒，速度 70。
4. **太近**（框高度 ≥ 80%）→ 停住，**绝不倒车**。
5. **对准过、一直没动的人**（比如睡觉、看电视的人）→ 不再反复调整。
6. 每动一下，都要等画面稳定、拿到新的识别结果，再决定下一步。
7. **以下情况不动**：助手被暂停、有人正在说话、“回去充电”后的 18 分钟冷却中。

**C. 找不到人时**
1. **5 分钟没看到人**：
   - 离充电座不远，或者位置不确定（比如程序刚重启）→ **直接回充电座**。
   - 走远了 → **转圈找人**。
2. **转圈找人**：每次转 30 度，共 24 次（两圈）。每停一个方向，用 **YOLOv9-s 320（onnxruntime，CPU）**自己看一眼：门槛 0.5，整张画面加左右两半各看一次；隔 1 秒再看一次，两次都看到才算。
3. 找到人 → 停止转圈，转过去跟。转满两圈还没人 → 回充电座。回充 5 分钟后还没开始充电，就再试一次。

**D. 后台定期做的事**
- **每 10 秒**读一次机器人状态（是否在充电），用来判断它在不在充电座上。
- 发现**桌面模式**开着就自动关掉（机器人一直在地上）。
- **每 6 小时**把夜视设成“自动”一次。

然后再提一个单纯是“巧了”的问题，它不是一个真正的问题。

本来设定的是，如果用户让他回去充电，他回到充电桩上是要冷却 10 分钟的，因为一般在这种场景下用户不想被他打扰。但我刚才观察到用户在用的时候，我很确定还没到 10 分钟，小机器人回到充电桩之后，哗的一下又出来了。

不过这其实是个乌龙：排查之后发现只是因为现在还在频繁修 bug，恰好在那个时间 Claude Code 给他发了一个重新部署的命令，导致服务重启了，他就忘了之前设定的冷却 10 分钟这回事。

我觉得这个无所谓，日常使用时本来也不会频繁部署、频繁重启，在日常场景中不是问题，不用怎么管。

如果之后还是觉得短，那就提到 25 分钟；如果嫌长，再往下降到 13、14 分钟左右.

补充一下：因为现在仍然处于一个频繁重启、性能 debug 的阶段，为了不太影响家人，我又在 dashboard 上加了个手动冷却的按钮。

总之现在的Token消耗量是可以的。

不过有点担心的一点是：它原本判断声音是不是来自电视的逻辑，是先 commit 进主 conversation 然后再去判断的。但这样的话，电视或视频的声音就会把整个聊天带偏。

所以我这边又处理了一下，把它们分开了：单独用同样的模型去做语音识别和判断。

至于为什么语音识别非得用 API，是因为如果用本地的 Whisper，处理时间有点太长了（而且主要是 Whisper 仍然挺吃电脑算力的。如果把它的识别模式开得好一点、让识别更精确一点，处理时间确实会翻好几倍，大概要两三秒的样子，真的不能这么干）。倒不是说真的会增加非常多延迟，而是原本的实验因为地理位置跨度就已经挺大了，我不太乐意再在这上面增加耗时。

claude code 补充（10-20）：

**1. 分开之后，对话中每一轮是这样走的**

1. 本地 WebRTC VAD 判断一句话说完了（没变）。
2. 边说边把声音实时发给单独的识别连接 **`qwen3-asr-flash-realtime`**（`asr_realtime.py`），**不发给对话模型**。
3. 说完后，识别连接 0.5～1.4 秒给出文字。以前用对话模型自带的转写，中位数 1.6 秒，慢的时候要 5 秒以上。
4. 和以前一样判断：没内容、不是在跟它说、让它闭嘴、让它回去充电。
5. 要回答，才把这一轮的音频一次性发给 **`qwen3.8-omni-flash-realtime`** 去回答。不回答的轮次，对话模型从头到尾都听不到。

上面「B. 对话中」第 2、3 步的顺序就是这样变的。识别连接断了会自动改用本地 Whisper，同时在后台重连（实测断开后约 1 秒就连上）；闲置 280 秒后测过，连接还在。

**2. 踩到的坑：`clear` 清不掉**

本来的方案是：边说边发给对话模型，不回答时再用 `input_audio_buffer.clear` 清掉。实测发现，只要这句话结尾带静音（真实录音都会带），服务端就已经把它切成一段存好了，`clear` 清不掉。更糟的是，下一次 commit 进去的反而是本该丢掉的那句，真正要回答的那句却丢了。文档里没写这个行为。

所以改成判断完再一次性发。代价是出声晚 0.2～0.9 秒，正好被更快的识别抵消，总的等待时间和以前差不多。

**3. 改之前它是怎么被带偏的（日志原文）**

- 10-19 早上，上下文里进了一段电视剧骂人的台词。之后妈妈说"其实我记得我怎么去过哈尔滨呢？也去旅游去"，它回"听你这一通说下来，感觉你心里憋屈得厉害……"
- 10-20 上午，一段音乐进了上下文。它先说"这歌听着挺温柔，是《小幸运》吧"；妈妈问"今天多少？"，它答"我听着像是《小幸运》，田馥甄唱的。"

这几场会话里，64%～96% 的轮次是电视、音乐或噪声。这些轮次转写出来是空的，但音频照样进了上下文。

**4. "谢谢"误唤醒**

10-20 的 06:02、07:36 和 10:58，它被"谢谢"叫醒了三次。查下来，这是本地 Whisper 在噪声上编出来的字，不是有人说话：同一段音频交给 Qwen 识别，结果是空的。

Whisper 的训练数据里有大量视频字幕，视频结尾常常是"谢谢观看""谢谢大家"，所以它在静音和杂音上很容易冒出这类话。三次都出现在 10-19 把 Whisper 从 base 换成 small 之后（base 编出来的是"请用简体字"）。

修法：待机时，如果整句话只有"谢谢""谢谢你""谢谢大家"这类客套话、又没有唤醒词，就不唤醒。"谢谢你猫猫"照常能叫醒。

**5. 顺手**

- 日志里每次回复都会记一行用量：`Response completed; usage: input …`，以后对账单不用再猜。
- 联网搜索没关。日志里每次回复的文字 tokens 一直稳定在 1200～1350，没有一次像是真的搜过网。开着它，每次回复固定多出约 300 tokens（搜索工具的说明），可以接受。
- 新的识别连接按秒计费（0.00033 元/秒），只算说话的片段，每天几毛钱。

加了一个早晨定时播报天气的功能：调用天气接口，把当地天气转成音频定时播放。这里也做了冲突处理（conflict handling）：如果当时有人正在说话就先不播，等说完再播，很常规的先后顺序处理。
4. 记忆架构踩坑（核心大问题）
前面那些都是小事，真正的大问题是这边的屎盆子终于炸了。

之前那套从0到1阶段，先冲速度、先跑通再说的"从沼泽里捡起一片玫瑰花瓣的横冲直撞"打法，在现在这种从 1 到 100 的阶段确实得改改了。我之前让 Claude Code 做 V3 版本重构时，明确跟它说了 memory 是双层 layer（从另外一个项目 Specter 那边搬过来的），之前用 OpenAI 的 V2 版本配合 Frigate 时本来也是这么跑的，效果一直很好。

结果这次做 V3 重构，Claude Code 把这事全给忘了。它之前一直不提 memory，有什么事就直接全改在环境变量里的 prompt 里。我当时虽然隐约觉得不对，但太信任它了，以为是它故意设计的，觉得这样能把身份信息搞得更牢，这事我和它一人一半锅。

排查才发现它根本没用双层记忆架构， 文件夹建了可是根本没程序用，即在记忆方面直接退回到了最初的 V1 版本：机器人完全没有记忆，每次 conversation 一结束什么都不剩。像"身体不适"这种有时效性的状态，它直接写进了环境变量的 prompt，导致机器人反复在那儿问。

现在已经让 Claude Code 赶紧把双层架构补回来了。以后还是得用 Spec 作为标准去规范开发，Opus 5.5 虽然比我聪明太多，但真的不能盲目信任。

昨天终于把 Anthropic 写的 Claude Code Best Practices 博客读完了。Anthropic 这家公司确实很有 hacker 和工程师精神，主要体现在对 context window 的控制上，给到了用户非常大的自由度和灵活性。虽然大部分内容过了一遍没有太深印象，但确实学到了一个特别实用的技巧：用 /btw（by the way）来插入指令，完全不影响主 conversation 的上下文。我现在已经在用 /btw 让它去检查部署状态、看有没有上线、做查错排查以及检查当天运行是否正常，这个功能确实太好用了。多看文档还是管用。

(a) 放宽了误触发场景下的语音过滤，只要家人说“安静”、“闭嘴”这类词，就让它安静一段时间
(b) 在我这边的 dashboard 上，增加了“安静”和“取消安静”的功能按键

Frigate 改用 GPU
为什么有这个更改？因为我这边打游戏开始卡了。查下来发现是 Frigate 在用 CPU 解码视频、跑人体检测，最多吃掉差不多 9 个核心。所以进行了一波优化：Frigate 的视频解码（NVDEC）和 YOLOv9 检测（ONNX / CUDA）都挪到了 RTX 4070 SUPER 上，CPU 留给游戏。现在显卡上检测一帧大约 5 毫秒。- 这是来自大概一周后的补充，就是这个事好像真的不是 Frigate 的问题。因为那个时候到底怎么样，也没办法查证了。但是当时打游戏卡这个事，它很可能是因为端口的问题。这个讲起来又是一件非常离奇的事情，我们从盘古开天地开始讲起吧，开个玩笑。

我简单叙述一下这个问题吧，先讲是怎么引出来的。那是因为前两天的一个晚上，我当时要用打印机去打印，然后发现出问题了，打印不出来。当时我是急着用这个文件，那就行吧，我让 Codex 你先别管 Codex 怎么干的，先把这个东西给我整出来吧。因为我这个打印机之前切换 WiFi 已经切了三回了，所以它确实是有一些连接上的问题，不过我记得是在之前解决掉了。这回我最开始只是觉得，是不是这个连接又有什么问题了，什么 IP 对不上了什么的，我真没多想。但是后来我看 Codex 去打印，它也费劲，就是我不知道怎么描述这件事情。我们正常的，它就是一份 PDF，点一下 Print，然后这打印机就一页一页吐出来了吗？但是这回不是，这回 Codex 那边我不知道他怎么搞的，反正他给我每一页都搞成一页打完，然后他去看，他去走下一个打印的任务，打印下一页。他不是一个文件一个文件打印，他是一页一页打印。

然后就查了一下这个是怎么回事，想让他跟我说我电脑上的这个 ephemeral port 已经 exhausted 了。我当时都惊了，就是因为这个东西是在 Task Manager 上查出来的，就是我起码的抓包思路还是有的。我当时确实是怀疑说，是不是我这个 CPU 占的 usage 太多了，或者说我 memory 满了什么的。但是我当时看 Task Manager 没有任何问题，你这个端口耗尽它也不在 Task Manager 上显示呀。它是后来才查出来的，然后又说，那你这个端口你怎么耗尽的呢？

因为我电脑还挺好的，然后查出来是半年前。在本地电脑上，Vibe Coding 的电脑使用时间记录这个软件非常之好用，我真的是个天才，它在我电脑上已经非常稳定地运行了几个月，一点事没有，所以我之前从来没有怀疑过是它的问题。然后是关于 TCP 握手那事，问题在于它的 TCP 四次挥手告别是有问题的，就是本地的 Local Server 端发现跟程序连不上之后，它没有完成这个挥手，没有释放掉每一个连接，就一直占着了。

那就还得谈到，为什么之前没发现呢？毕竟它已经稳定运行了好几个月了，我就没有再去给它改过代码了。那是因为它每天凌晨 4 点自动重启，就把之前占用的端口给释放了。就这样，莫名其妙这两个 bug 能 work 了。好吧，也不叫 bug，就是莫名其妙地给抵消掉这个问题了。

到后来肯定解了，解的办法就很简单嘛，就是让 Server 端正儿八经地在四次挥手的时候，把连接的 Port 放出来，不要再占着连接了。这个事情就非常简单地完事了。但是我只是说，当时那个游戏的问题，它真的可能不是 Frigate 的锅

找降噪：GLM 太贵，千问的连接也不换成 WebRTC（11-05）
起因是电视声太吵，想找降噪。v1 用的 OpenAI 有远场降噪（far_field），电视开着也不容易误触发，千问的实时接口没有这个参数。

先查了别家：智谱的 GLM-Realtime 有内置降噪，也有远场模式。可它按分钟收费（0.18~0.3 元/分钟），千问按 token 收费。按家里实际的用量估算，GLM 要贵 10 倍以上，最多可能差几十倍。机器人大部分时间都不说话，按分钟算很不划算，所以不用。

再看千问自己：文档里说，用 WebRTC 方式接入"内置回声消除和降噪"，我们现在用的是 WebSocket，所以想过要不要换。

最后也没换，原因有三个：
1. 降噪大概率用不上：文档的示例靠浏览器，我们在服务器上只能用 Python 的库（aiortc），那层降噪很可能是浏览器自带的。就算能用，估计也跟已经开着的声网降噪差不多。
2. 改动很大：WebRTC 方式不支持手动模式，声音直接进对话模型。"判断是不是在跟它说话"、"把文字发给模型"、"往机器人喇叭推声音"这几条都得重做。
3. 更贵：现在发给对话模型的是文字（1.5 元/百万 token），换了以后要发声音（6 元/百万 token）。

当时先试了成本低的 semantic_vad（让服务端判断一句话说完没有），跑了一个晚上漏听太多，没用。

补充（11-08）：WebRTC 本身用 Opus 压缩，如果当时换了，下面这次上传太慢的问题可能会轻一些。但识别那一路已经直接改成了 Opus，带宽问题解决了，上面三个原因也都还在，所以还是不换。

机器人突然不说话（11-08）
家里人反馈机器人不理人，看板上全是 "No transcript within 8s; ignoring turn"。

问题：程序跑在我这边（多伦多），家里人说的话要从这边传到阿里云北京转成文字。国内晚上（北京时间下午 5 点以后）跨境线路被限速，这边往北京的上传只剩大约 35 KB/s，可原来的音频格式（PCM）每秒要传大约 43 KB。传不完的越积越多，文字越回越晚，最后晚了 30 多秒。程序等 8 秒没等到文字，就当没人说话，所以机器人一句都不回。

解决：声音先压缩成 Opus 格式再送去识别，数据量只有原来的大约十分之一，识别出来的文字一样准。测了一下，连续说 90 秒，文字都在 2 秒内回来；原来最慢要 26 秒，中途还会断线。

以后把程序搬到国内的服务器上，就不会有这个问题了：机器人、程序、阿里云都在国内，不用走跨境这条被限速的线路。

详细经过（时间线、怎么查出来的、技术细节）：[docs/incident-2026-11-08-robot-silent.md](docs/incident-2026-11-08-robot-silent.md)

机器人有文字回复，但没有声音（11-08）
上面识别的问题修好以后，看板上能看到机器人的文字回复了，但家里人还是听不到它说话。

问题：机器人用的声网通话凭证大约 24 小时过期，程序每 20 小时自动续一次，续的时候会断开再重连。续期这段代码漏了一步：没有先停掉往机器人推声音的那个线程。它一直往已经断开的旧连接里推声音，也不报错，日志照样写"播放了多少毫秒"；新连接却从来没真正发声。所以从 11-07 晚上（多伦多时间）那次续期之后，机器人哑了大约 13 个小时。早上家里人说它不说话，其实是识别慢和没声音两个问题叠在了一起。

解决：续期之前先停掉旧的推声音线程，跟唤醒机器人时的做法一样。重启以后去听了一下，能听到回答了。

搬到国内云服务器：要多大的机器、多少钱（11-08）
问题：程序跑在我这边，离机器人和阿里云都太远，晚上还会被跨境限速，所以打算把程序搬到北京阿里云的云服务器上。搬之前得先弄清楚：要多大的机器，一个月多少钱，内存能不能省一点。

结论：
- 配置：现在三个主要容器一共占大约 4 GB 内存。4 核 8G 最稳；先瘦身的话，2 核 4G 很有希望够用。必须是 x86 机器（机器人用的声网 SDK 只有 x86 版），不用买带显卡的。
- 价格：阿里云轻量服务器 4 核 8G 按月付大约 220 元一个月，最贵；买一年大约 1159 元，合每月不到 100 元。2 核 4G 活动价大约 199 元一年。不买三年。
- 把几个容器合并成一两个，省不了内存。容器只是把程序隔开，本身几乎不占内存，内存是里面的程序用的，合到一起加起来还是那么多。
- 真正能省内存的办法：Frigate 从显卡改回 CPU。现在它的检测进程占 1.1 GB，主要是加载了显卡的运算库，改成 CPU 估计只要两三百 MB，能省大约 800 MB。另外 Whisper 换小一号的模型，还能再省几百 MB。改 CPU 后检测准确度不变，只是每帧慢几十毫秒，跟人感觉不出来。
- 为什么 YOLO 模型会有两份：Frigate 只看画面里动的地方，还要连续好几次看到才算有人，所以躺在沙发上不动的人经常被漏掉。所以机器人转圈找人时，assistant 每转到一个方向就自己拍一张，用同一个 YOLO 再仔细看一遍。同一双眼睛，两种用法，这一份不去掉。

下一步：先开一台按小时付费的机器试两三天，在上面把整套限制在 2 核 4G 里跑一晚上，跑得住就买 2 核 4G。详细计划在 docs/china-cloud-plan.md。

今天过了一下国内云厂商的一些主机，发现真的挺贵的。因为这个程序最低要求是 2 核 4G，其实 2 核 4G 真的非常紧巴巴的。2 核 4G 的基本价格得在 150~200 元/年，哪怕这已经是活动价，已经是很优惠的价格了。如果是正儿八经去买，真正的价格应该在 500 元/年左右。其实这个程序还是挺重的，真的还挺重的，它对 CPU 的消耗还是挺有要求的，而且一定是要求要一个独占的 CPU。所以其实 4 核 8G 才是它一个最合理、最合适的状态。我不想天天因为一些什么 Server 莫名其妙的 CPU 占满了、Memory 占满了这种破问题，然后再让程序波动。如果这种问题就是让我做维护，天天因为点硬件顶不住来虚耗心神，这就很没有价值。那就接着谈，当前查到的 4G 和 8G 又是什么样的状态？4G 和 8G 这边让muse过了一遍国内大大小小的新旧云厂商，基本上价格就得在 500~1000 一年之间了，那其实我自己觉得，这一年花接近 1000 的价格，因为 500 真的少，500 的只有华为的 HECS 4 核 8G。这个还不是 500，它那个带宽还得另算，我还没把带宽这个事给它加进去呢。反正总之，如果是说 4 核 8G，那么基本上主流、非主流的云厂商，它提供这一年的服务，就得要八九百，就得到 900~1000 出头了 ； 在这种情况下，这个就非常不划算，还不如自己买一台小主机呢。可是自己买一台小主机，然后一直都放在国内的家里，它的问题就是我人不在那儿，这种tech heavy问题，我人不在就很难搞。所以综上所述，这个转地方部署的问题，真的延后再议吧。我让 muse 再给我接着去盯这件事情。如果有一个非常非常好的 deal，那我可能会再去生出这部分的想法。可是如果它仍然都是这个样子的话，就这么不 cost effective，那我觉得其实现在的一个程序状态我也能接受
